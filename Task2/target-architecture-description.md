## Использованные архитектурные стили

Целевая архитектура сочетает несколько стилей интеграции:

* **Синхронное взаимодействие «запрос - ответ»** используется там, где пользователю нужен немедленный результат: вход, чтение профиля и результатов анализов, получение свободных слотов, запуск операции и проверка её состояния.
* **Архитектура, управляемая событиями (EDA),** используется для передачи свершившихся бизнес-событий: подтверждения записи, успешной оплаты, появления результата анализа и отправки уведомления. Отправитель не ждёт завершения обработки, а получатели работают независимо друг от друга.
* **Пакетная обработка** не используется в основном пользовательском сценарии. Она применяется только для контрольной сверки и повторной доставки пропущенных лабораторных результатов.
* **Saga с оркестрацией** управляет процессом записи и оплаты. Оркестратор хранит состояние каждого шага, запускает компенсирующие действия при ошибке и продолжает выполнение после перезапуска.
* **Антикоррупционный слой (Anti-Corruption Layer, ACL)** изолирует мобильный контур от нестабильных контрактов LIS, 1С и платёжного шлюза. Он преобразует протоколы и форматы, но не содержит бизнес-логику процесса записи.
* Для надёжной передачи событий используются **транзакционный исходящий журнал (Transactional Outbox)**, доставка **как минимум один раз (at-least-once)** и журнал обработанных сообщений **Inbox**. Событие сохраняется вместе с бизнес-операцией, а повторная доставка не приводит к повторному выполнению действия.

## Обоснование новых интеграций

| Новая интеграция                                                        | Стиль и механизмы                                                                                                                                      | Обоснование                                                                                                                                                                                                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Мобильное приложение -> сервис аутентификации**                        | Синхронное взаимодействие, `OIDC Authorization Code + PKCE`, короткоживущий токен доступа и токен обновления                                           | Это стандартный поток входа для мобильного приложения, в котором нельзя безопасно хранить секрет клиента. Пароль не передаётся в Patient API, а PKCE защищает перехваченный код авторизации.                                                        |
| **Мобильное приложение / веб-портал -> API Gateway**                     | Синхронный `HTTPS/REST`, JWT, ограничение частоты запросов, WAF                                                                                        | Пользователю нужен немедленный ответ. Шлюз создаёт единую внешнюю точку входа, проверяет токен, ограничивает нагрузку и маршрутизирует запросы. Бизнес-логика в шлюзе не размещается.                                                               |
| **API Gateway -> Patient API**                                           | Синхронный `REST/JSON`; серверный слой без локального состояния для мобильного приложения                                                              | Patient API предоставляет контракт для мобильного приложения и скрывает внутренние системы. Отсутствие локального состояния позволяет запускать несколько экземпляров сервиса за балансировщиком.                                                   |
| **API Gateway -> сервис аутентификации**                                 | Локальная проверка JWT по кэшированному JWKS; периодическое обновление ключей                                                                          | Вызов сервиса аутентификации на каждый запрос увеличил бы задержку и создал дополнительную точку отказа. Локальная проверка подписи сохраняет быстрый путь обработки.                                                                               |
| **Patient API -> CRM**                                                   | Защищённый синхронный `REST`: тайм-аут, ограниченные повторные попытки для безопасных операций и автоматический выключатель (Circuit Breaker)          | Данные профиля нужны в текущем ответе. Тайм-аут и автоматический выключатель не дают сбою CRM распространиться на всю серверную часть мобильного приложения.                                                                                        |
| **Patient API -> сервис результатов анализов**                           | Синхронное чтение из отдельной модели для чтения; курсорная пагинация                                                                                  | Пациенту нужен быстрый ответ, но чтение не должно нагружать CRM и LIS. Отдельную модель можно масштабировать независимо, а курсорная пагинация не нарушается при появлении новых результатов.                                                       |
| **LIS -> интеграционный слой -> Kafka / CRM**                             | Синхронный идемпотентный приём с надёжной фиксацией, затем асинхронная доставка; пакетная контрольная сверка как резервный механизм                    | LIS получает подтверждение только после сохранения результата. Временная недоступность CRM или другого получателя не приводит к потере данных. Пакетная сверка восстанавливает пропущенные результаты, но не задерживает обычную обработку.         |
| **Kafka -> сервис результатов анализов**                                 | Событийная доставка как минимум один раз, журнал Inbox и устранение дублей по `eventId`                                                                | Результат сохраняется в Kafka и переживает временную недоступность сервиса. Повторная доставка безопасна, поскольку сервис проверяет `eventId` и не создаёт дубли. Kafka также позволяет повторно прочитать события и подключить новых получателей. |
| **Patient API -> оркестратор записи и оплаты**                           | Синхронное создание процесса с `Idempotency-Key`; ответ `202 Accepted` и `operationId`; дальнейшее выполнение через Saga                               | Мобильное приложение не должно ждать завершения медленного платежа. Оно получает идентификатор операции и может безопасно повторить запрос или проверить состояние процесса.                                                                        |
| **Оркестратор -> Расписание**                                            | Защищённый синхронный `REST`, идемпотентные команды, тайм-аут, ограниченные повторные попытки и автоматический выключатель                             | Перед продолжением процесса нужно однозначно определить, зарезервирован ли слот. Здесь согласованность важнее доступности. Повторная команда с тем же ключом не должна создавать вторую запись.                                                     |
| **Оркестратор -> ACL -> платёжный шлюз**                                  | Синхронные идемпотентные команды с `operationId`; API проверки состояния при неопределённом результате; тайм-аут и автоматический выключатель          | После тайм-аута нельзя выполнять новую оплату, поскольку деньги уже могли быть списаны. Оркестратор проверяет состояние той же операции. При ошибке последующих шагов Saga отменяет запись или запускает возврат.                                   |
| **Patient API -> ACL -> 1С**                                              | Синхронное чтение через кэш; тайм-аут, автоматический выключатель и ограниченные повторные попытки; резервный ответ по последним подтверждённым данным | Проверка полиса нужна пользователю сразу, но 1С нестабильна и не выдерживает пиковую нагрузку. Кэш снижает число обращений к 1С, а защитные механизмы не дают её сбою остановить мобильное приложение.                                              |
| **Оркестратор / Расписание / сервис результатов -> Kafka -> Уведомления** | Асинхронная публикация и подписка, доставка как минимум один раз, отдельные группы потребителей и очереди ошибочных сообщений (DLQ)                    | Отправка push, SMS и электронной почты не должна задерживать запись, оплату или публикацию результата анализа. Получатели независимо обрабатывают события, а ошибочные сообщения можно отправить на повторную обработку.                            |
| **Все интеграционные компоненты -> платформа наблюдаемости**             | Асинхронная передача трассировок OpenTelemetry, метрик и структурированных журналов; единый `traceId`                                                  | Сквозная трассировка связывает запрос мобильного приложения, шаги Saga, вызовы устаревших систем и события Kafka. Это ускоряет поиск причины сбоя и позволяет контролировать `p99`, доступность, задержку обработки событий и ошибки интеграций.    |

## Надёжность и масштабирование

* API Gateway, Patient API, оркестратор и антикоррупционный слой запускаются в нескольких экземплярах без локального состояния за балансировщиком нагрузки.
* Состояние Saga, ключи идемпотентности, исходящие события, журнал обработанных сообщений и модели для чтения хранятся во внешних отказоустойчивых хранилищах.
* Для синхронной операции задаётся общий предел времени выполнения. Повторные попытки разрешены только для идемпотентных операций и не должны выходить за этот предел.
* Для оплаты и создания записи обязательны `operationId` или `Idempotency-Key`. Результат первой обработки сохраняется и возвращается при повторном запросе.
* Каждое событие содержит `eventId`, `eventType`, `timestamp`, `aggregateId`, `payload`, версию схемы и `traceId`.
* Kafka масштабируется увеличением числа разделов. Для событий записи ключом служит `bookingId`, для результатов анализов - `patientId` или `analysisId`. Это сохраняет порядок событий в пределах одной сущности.
* RabbitMQ остаётся внутренним механизмом сервиса уведомлений. Очереди разделяются по каналам и типам задач, имеют ограничения, очередь ошибочных сообщений и контроль задержки обработки.

## Этапность внедрения

В первую версию мобильного приложения входят API Gateway, сервис аутентификации, Patient API, идемпотентный процесс записи и оплаты, интеграция с уведомлениями и сквозная трассировка. Новые интеграции сразу работают через целевые контракты, поэтому мобильное приложение не зависит от контрактов устаревших систем.

На следующем этапе разворачиваются событийная платформа, отдельная модель результатов анализов, контрольная сверка лабораторных данных, кэш полисов и горизонтальное масштабирование компонентов. Диаграмма показывает целевое состояние архитектуры через год, а не временное решение для первой версии.
