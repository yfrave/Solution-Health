# Надёжная доставка результатов анализов

Готовая блок-схема: [lab-results-flow.png](./lab_results_flow.png). Исходник: [lab-results-flow.puml](./lab-results-flow.puml).

## Выбранное решение

Для доставки результатов используется следующий поток:

**LIS -> сервис приёма результатов -> Kafka -> сервис результатов -> мобильное приложение**

LIS остаётся основной системой хранения медицинских результатов. Сервис результатов хранит отдельную копию данных, 
подготовленную для быстрого чтения через мобильное приложение. Само приложение не обращается напрямую к LIS или CRM.

После готовности анализа LIS отправляет результат в REST API сервиса приёма. Запрос содержит:

* `eventId` - идентификатор события;
* `analysisId` - идентификатор анализа;
* `patientId` - идентификатор пациента;
* `version` - версия результата;
* данные результата.

Если изменить LIS нельзя, перед ней устанавливается адаптер. Он получает готовые результаты через существующий REST API 
и передаёт их в новый сервис.

Сервис приёма сначала сохраняет результат в своей базе данных. В той же транзакции он добавляет запись в журнал `Outbox`. 
После успешного сохранения LIS получает подтверждение.

Отдельный обработчик читает `Outbox` и публикует событие `LabResultPublished.v1` в Kafka. Если Kafka временно 
недоступна, запись остаётся в журнале и будет отправлена позже.

Сервис результатов получает событие из Kafka и проверяет `eventId`. Обработанные события сохраняются в журнале `Inbox`, 
поэтому повторная доставка не создаёт второй результат. После этого сервис обновляет данные, доступные мобильному приложению.

Когда результат сохранён, публикуется событие `LabResultAvailable.v1`. Сервис уведомлений получает его и отправляет пациенту push-уведомление.

Мобильное приложение запрашивает результат через API Gateway, Patient API и API сервиса результатов. 
Другие сервисы не обращаются к базе сервиса результатов напрямую.

Используется доставка **как минимум один раз (at-least-once)**. Одно событие может прийти повторно, 
но благодаря `Inbox`, `eventId` и ограничению `(analysisId, version)` оно будет применено только один раз.

## Сравнение вариантов

| Вариант                                                  | Задержка                          | Надёжность                                                                                                                          | Масштабирование                                                    | Сложность эксплуатации                                                                                    | Решение                                                                                               |
| -------------------------------------------------------- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| **Синхронный REST: LIS -> CRM -> приложение**              | Низкая, если все системы работают | Сбой CRM останавливает передачу. После тайм-аута неизвестно, был ли результат сохранён. Возможны потери и дубли                     | LIS и CRM становятся общими узкими местами                         | Реализовать просто, но при сбоях нужны повторные запросы и ручное восстановление                          | **Не выбран.** Повторяет проблемы текущей архитектуры                                                 |
| **FTP и пакетная обработка**                             | Минуты или часы                   | Пакет можно передать повторно, но нужно проверять полноту файлов и устранять дубли                                                  | Подходит для больших пакетов, но создаёт нагрузку во время запуска | Нужен контроль файлов и автоматический повтор неудачных загрузок                                          | **Только резервный вариант.** Не обеспечивает быструю доставку                                        |
| **RabbitMQ**                                             | Секунды                           | Поддерживает подтверждение обработки, повторные попытки и очередь ошибочных сообщений                                               | Можно запускать несколько обработчиков                             | Уже используется в компании, но текущая очередь переполняется. Повторное чтение старых событий ограничено | **Подходит для уведомлений**, но не выбран для хранения медицинских событий                           |
| **Kafka с Outbox, Inbox и отдельной моделью для чтения** | Секунды                           | Outbox защищает от потери при публикации, Inbox - от повторной обработки. Контрольная сверка восстанавливает пропущенные результаты | Разделы Kafka позволяют обрабатывать разные анализы параллельно    | Требуются настройка Kafka, контроль очередей и обработка ошибочных сообщений                              | **Выбран.** Поддерживает повторное чтение событий, несколько получателей и работу при временных сбоях |

## Обработка сбоев

| Сбой                                     | Поведение системы                                                                                                                   |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Сервис приёма результатов недоступен** | LIS или адаптер повторяет запрос с тем же `eventId`. Интервал между попытками постепенно увеличивается                              |
| **Kafka временно недоступна**            | Результат уже сохранён вместе с записью Outbox. Обработчик отправит событие после восстановления Kafka                              |
| **Сервис результатов остановлен**        | События остаются в Kafka. После запуска сервис продолжит обработку с последней подтверждённой позиции                               |
| **Получено некорректное событие**        | Система несколько раз пытается обработать событие. Если ошибка сохраняется, оно переносится в очередь ошибочных сообщений           |
| **Событие пришло повторно**              | Сервис находит `eventId` в журнале Inbox и не выполняет повторное обновление                                                        |
| **Результат не был передан из LIS**      | Периодическая сверка сравнивает результаты LIS с принятыми событиями и повторно отправляет отсутствующие                            |
| **CRM недоступна**                       | Обновление CRM выполняется отдельным обработчиком после восстановления. Результат при этом остаётся доступен в мобильном приложении |

## Масштабирование и эксплуатация

* Сервис приёма результатов, сервис результатов, обработчик Outbox и Patient API запускаются в нескольких экземплярах.
* Эти компоненты не хранят рабочее состояние в памяти конкретного экземпляра.
* Поток Kafka разделяется по `analysisId`. Версии одного анализа обрабатываются по порядку, а разные анализы - параллельно.
* Количество обработчиков можно увеличивать вместе с количеством разделов Kafka.
* Данные для мобильного приложения индексируются по `(patientId, completedAt, analysisId)`.
* Система контролирует задержку обработки, количество ошибочных сообщений и возраст записей в Outbox.
* Каждое событие содержит `eventId`, `eventType`, `occurredAt`, `analysisId`, `patientId`, `version`, `traceId`, `payload` и версию схемы.
* Внутренние соединения защищаются с помощью mTLS. Медицинские данные шифруются при передаче и хранении.
* Patient API получает идентификатор пользователя из проверенного JWT и проверяет принадлежность результата пациенту.
* RabbitMQ используется только внутри сервиса уведомлений и не становится общей очередью для всех событий.
