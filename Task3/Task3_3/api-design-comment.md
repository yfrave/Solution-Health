# API предстоящих записей пациента

Спецификация: [appointments-api.yaml](./appointments-api.yaml).

Для получения списка записей используется метод:

```http
GET /api/v1/appointments
```

Метод `GET` выбран потому, что запрос только читает данные и не изменяет состояние системы. Повторный вызов возвращает 
тот же результат, если данные записей не изменились.

Идентификатор пациента не передаётся в адресе или параметрах запроса. API Gateway проверяет JWT и передаёт 
идентификатор пользователя `sub` в Patient API. После этого Patient API определяет связанного с ним пациента. 
Пользователь не сможет получить чужие записи простой заменой `patientId`.

## Пагинация

По условию задания используются параметры `limit` и `offset`:

* `limit` задаёт количество записей в ответе: от 1 до 100, значение по умолчанию - 20;
* `offset` задаёт количество пропускаемых записей: от 0, значение по умолчанию - 0;
* `total` содержит общее количество найденных записей;
* `hasMore` показывает, остались ли следующие записи.

Записи сортируются по дате начала и идентификатору:

```text
startsAt ASC, id ASC
```

Дополнительная сортировка по `id` нужна для случаев, когда несколько записей имеют одинаковое время начала.

Пагинация через `limit` и `offset` подходит для небольшого списка записей одного пациента. Она проста в реализации 
и позволяет перейти к нужной позиции.

У этого подхода есть ограничение: если между запросами запись будет добавлена или отменена, содержимое соседних страниц 
может измениться. Для больших и часто меняющихся списков лучше подходит курсорная пагинация. 
В этом задании `limit` и `offset` достаточно.

## Версионирование

Версия API указывается в адресе:

```text
/api/v1/appointments
```

Такой вариант понятен мобильному приложению и позволяет одновременно поддерживать `/v1` и `/v2` во время перехода на новую версию.

Новая версия создаётся только при несовместимом изменении, например:

* удалении или переименовании поля;
* изменении типа поля;
* изменении смысла существующего поля;
* изменении обязательности поля.

Добавление нового необязательного поля не требует перехода на `/v2` и может выполняться внутри `/v1`.

Перед отключением старой версии нужно заранее указать срок её поддержки, чтобы мобильное приложение успело перейти 
на новую версию API.

## Аутентификация и ошибки

Метод защищён с помощью OIDC и токена доступа JWT. В спецификации используется схема `bearerAuth`.

Мобильное приложение передаёт токен в заголовке:

```http
Authorization: Bearer <access_token>
```

API Gateway проверяет:

* подпись токена;
* срок действия;
* издателя `iss`;
* получателя `aud`;
* необходимые права доступа.

Спецификация содержит три требуемых варианта ответа:

* `200 OK` - список предстоящих записей и данные пагинации;
* `401 Unauthorized` - токен отсутствует, просрочен или не прошёл проверку;
* `500 Internal Server Error` - внутренняя ошибка сервера.

При ошибке `500` клиент получает безопасное сообщение и `traceId`, по которому можно найти запрос в журналах. 
Внутренние сведения об ошибке и трассировка стека в ответ не передаются.
