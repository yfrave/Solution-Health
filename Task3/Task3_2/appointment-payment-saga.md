# Запись к врачу с оплатой и резервированием лаборатории

Готовая диаграмма: [appointment-saga-sequence.png](./appointment_saga_sequence.png). Исходник: [appointment-saga-sequence.puml](./appointment-saga-sequence.puml).

## Успешный сценарий

1. Мобильное приложение отправляет запрос с заголовком `Idempotency-Key`.
2. Patient API передаёт запрос оркестратору. Оркестратор в одной транзакции создаёт экземпляр Saga и запись идемпотентности, после чего возвращает `202 Accepted` с `operationId`.
3. Оркестратор проверяет полис ДМС и определяет сумму, которую должен оплатить пациент.
4. Оркестратор временно резервирует слот врача. Если требуется лабораторное исследование, дополнительно резервируется время забора биоматериала.
5. После успешного резервирования оркестратор выполняет оплату с тем же `operationId`.
6. Оркестратор подтверждает запись к врачу и лабораторную резервацию.
7. Saga переводится в состояние `COMPLETED`. В той же транзакции создаётся запись в транзакционном исходящем журнале `Outbox`.
8. Итоговое событие публикуется в Kafka, после чего сервис уведомлений отправляет push-уведомление.
9. Мобильное приложение может в любой момент запросить состояние процесса по `operationId`.

## Выбор типа Saga

Используется **Saga с оркестрацией**. Процесс включает проверку полиса, резервирование двух слотов, оплату, условный 
шаг лаборатории и компенсирующие действия в обратном порядке.

Оркестратор хранит состояние каждого шага и позволяет службе поддержки определить, где остановился процесс. 
При хореографии контроль ветвлений, восстановление и аудит были бы распределены между несколькими сервисами. 
Это усложнило бы диагностику и повторный запуск процесса.

Мобильное приложение не ждёт завершения всей операции. После создания Saga оно получает `202 Accepted` и `operationId`. 
Оркестратор продолжает выполнение, а итоговый результат передаётся через API состояния и уведомление.

## Компенсирующие транзакции

| Шаг сценария                                   | Компенсирующее действие                                                                                                                                 | Устраняемый риск                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| **Резервирование слота врача**                 | Команда `cancelDoctorReservation(reservationId, operationId)` освобождает временно занятый слот. Повторная отмена возвращает результат первой обработки | Слот не остаётся занятым после ошибки лаборатории или оплаты. Не возникает запись без завершённого процесса           |
| **Резервирование времени забора биоматериала** | Команда `cancelLabReservation(labReservationId, operationId)` отменяет лабораторную резервацию. Если шаг не выполнялся, компенсация пропускается        | Лабораторный слот не удерживается для незавершённой или неоплаченной записи                                           |
| **Списание оплаты**                            | Идемпотентная команда `refundPayment(paymentId, operationId)` возвращает сумму исходной платёжной операции                                              | Пациент не остаётся без денег, если запись не была подтверждена. Повторная компенсация не создаёт несколько возвратов |

Компенсации запускаются только для успешно выполненных шагов и идут в обратном порядке:

1. возврат оплаты;
2. отмена лабораторной резервации;
3. отмена резервации слота врача.

Проверка полиса только читает данные и не требует компенсации.

Если компенсирующее действие временно недоступно, Saga переходит в состояние `COMPENSATION_PENDING`. 
Оркестратор выполняет ограниченные повторные попытки. После исчерпания попыток создаётся инцидент для ручного разбора. 
Состояние процесса и причина ошибки сохраняются в журнале Saga.

## Идемпотентность входного запроса

Мобильное приложение создаёт UUID `Idempotency-Key` для одной попытки записи. Если ответ потерян или получен тайм-аут, 
приложение повторяет запрос с тем же ключом.

Оркестратор хранит ключ в таблице `idempotency_requests` с уникальным ограничением:

```text
(patient_id, operation_type, idempotency_key)
```

В одной транзакции создаются:

* запись `idempotency_requests` со статусом `IN_PROGRESS`;
* хэш нормализованного тела запроса;
* идентификатор `operationId`;
* экземпляр Saga со статусом `STARTED`;
* первая запись в журнале Saga или команда Outbox на запуск процесса.

При повторном запросе действуют следующие правила:

* тот же ключ и то же тело запроса - возвращаются существующий `operationId` и текущее состояние процесса;
* тот же ключ с другим телом - возвращается `409 Conflict`;
* два одновременных запроса - уникальное ограничение позволяет создать только одну Saga, второй запрос получает уже созданный результат;
* завершённая операция - возвращается сохранённый итог независимо от того, получил ли клиент первоначальный ответ.

Один `operationId` передаётся во все команды расписанию, лаборатории и платёжному шлюзу. Каждая команда дополнительно 
содержит тип действия или отдельный `commandId`.

Участники сохраняют результат обработки с уникальным ограничением:

```text
(operation_id, command_type)
```

Например, команды `RESERVE`, `CONFIRM` и `CANCEL` относятся к одной операции, но считаются разными действиями. 
Повтор той же команды возвращает сохранённый результат и не выполняет действие второй раз.

После тайм-аута платёжной операции оркестратор сначала запрашивает её состояние по тому же `operationId`. 
Новое списание не создаётся, пока платёжный шлюз не подтвердит, что исходная операция отсутствует.

Для защиты от одновременного выполнения одного шага используется оптимистическая блокировка по полю `version` 
в записи Saga. Если два обработчика пытаются обновить Saga одновременно, изменение применяет только один из них.

Запись идемпотентности хранится дольше максимального периода повторных запросов и выполнения Saga. 
Журнал Saga сохраняется отдельно для аудита и разбора инцидентов.
