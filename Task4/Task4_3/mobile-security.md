# Базовые меры безопасности

## Аутентификация мобильного приложения

Для входа пациентов используется **OpenID Connect поверх OAuth 2.0 с потоком Authorization Code и PKCE (`S256`)**.

Мобильное приложение считается публичным клиентом, потому что в нём нельзя безопасно хранить `client_secret`. 
Вход выполняется через системный браузер или защищённую системную вкладку. Встроенный WebView не используется.

Перед входом приложение создаёт:

* `code_verifier`;
* `code_challenge`;
* `state`;
* `nonce`.

Сервис аутентификации проверяет данные пациента и при необходимости запрашивает второй фактор. 
После успешного входа он возвращает одноразовый код авторизации через заранее зарегистрированную 
ссылку приложения Universal Link или App Link.

Приложение отправляет код авторизации и `code_verifier` в сервис аутентификации по TLS и получает:

* токен доступа сроком действия **10 минут**;
* токен обновления сроком действия до **30 дней**.

Токен доступа хранится только в памяти приложения. Токен обновления хранится в iOS Keychain или Android Keystore. 
При каждом обновлении выдаётся новый токен, а предыдущий перестаёт действовать. Если старый токен повторно используется, 
вся связанная с ним сессия отзывается.

Каждый запрос к API передаёт токен доступа в заголовке:

```http
Authorization: Bearer <access_token>
```

Токены нельзя передавать в URL, хранить в cookie приложения или записывать в журналы и аналитику.

API Gateway проверяет:

* подпись JWT по ключам JWKS;
* издателя `iss`;
* получателя `aud`;
* срок действия `exp`;
* время начала действия `nbf`;
* права доступа.

После проверки API Gateway передаёт в Patient API идентификатор пользователя `sub`. Patient API самостоятельно 
связывает его с пациентом. Значение `patientId`, полученное от клиента, не используется как основание 
для доступа к медицинским данным.

При выходе из приложения токен обновления отзывается. Токен доступа перестаёт работать после окончания короткого срока действия.

Такой подход соответствует рекомендациям [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636) и [OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html).

## Ограничение частоты запросов

На API Gateway используется алгоритм **Token Bucket** с хранением счётчиков в Redis. Он разрешает короткий всплеск 
запросов, но ограничивает их среднее количество.

Указанные значения являются начальными и уточняются после нагрузочного тестирования.

| Тип запроса                                                  | Лимит                                                                                                                                                                             | Действие при превышении                                                                                                                                                                                                                   |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Публичный поиск врачей** `GET /api/v1/doctors`             | **60 запросов в минуту** на сочетание `IP + installationId`, кратковременный всплеск - до **20 запросов**                                                                         | API Gateway не передаёт запрос в сервис и возвращает `429 Too Many Requests`, код `RATE_LIMIT_EXCEEDED` и заголовок `Retry-After`. При постоянном превышении WAF может временно заблокировать источник. Успешные ответы поиска кэшируются |
| **Создание записи к врачу** `POST /api/v1/booking-processes` | **5 новых операций в минуту** и **20 операций в час** на пациента `sub`, кратковременный всплеск - до **2 операций**. Дополнительное ограничение - **30 запросов в минуту на IP** | API Gateway возвращает `429` и `Retry-After`. Новая Saga не создаётся. Повтор запроса с тем же `Idempotency-Key` возвращает существующий `operationId` и не считается новой записью. Попытка сохраняется в журнале безопасности           |

Ограничение частоты запросов не заменяет проверку прав, идемпотентность и защиту от DDoS-атак.

Внешние запросы проходят несколько уровней защиты:

```text
Защита от DDoS -> WAF -> API Gateway -> внутренние сервисы
```

На уровне сервисов дополнительно используются тайм-ауты, изоляция ресурсов и автоматические выключатели.

## Защита каналов и передаваемых данных

1. Все внешние соединения используют HTTPS. Предпочтительная версия - TLS 1.3, минимальная - TLS 1.2. Включается HSTS и обязательная проверка сертификата сервера. Описание TLS 1.3 приведено в [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446).

2. Между API Gateway и внутренними сервисами используется mTLS. Он шифрует соединение и позволяет обеим сторонам проверить сертификаты друг друга.

3. Сертификаты автоматически выдаются и обновляются с помощью Vault или cert-manager. Закрытые ключи не хранятся в исходном коде, образах контейнеров и Git-репозитории.

4. Подключения к Kafka, RabbitMQ, PostgreSQL и Redis также защищаются TLS. Для каждого сервиса создаётся отдельная учётная запись с минимально необходимыми правами.

5. Медицинские и персональные данные передаются только в теле запроса или ответа. Их нельзя помещать в URL и параметры запроса.

6. Push-уведомление не содержит диагноз, результат анализа, ФИО или другие медицинские данные. Допустимое сообщение: «Результат анализа готов».

7. Patient API при каждом запросе проверяет, что запрошенная запись или результат принадлежит пациенту из проверенного `sub`. Подмена `patientId` не должна давать доступ к чужим данным.

8. Все входные данные проверяются по типу, длине и допустимому формату. Для работы с базой используются параметризованные запросы. Сборка SQL через объединение строк запрещена. Это защищает систему от SQL-инъекций.

9. WAF дополнительно блокирует известные вредоносные запросы, но не заменяет проверку данных и параметризованные SQL-запросы внутри приложения.

10. Токены, коды авторизации, секреты и полные ответы с медицинскими данными не записываются в журналы, систему мониторинга и отчёты об ошибках. Для поиска запроса используется случайный `traceId`, который не содержит персональные данные.

11. Секреты хранятся в отдельном защищённом хранилище и регулярно меняются. Они не передаются через исходный код, сборочные файлы или мобильное приложение.

12. Для защиты от повторного использования запросов применяются PKCE, `state`, `nonce`, короткий срок действия токена, обновление refresh-токена и `Idempotency-Key`.

13. Базы данных и резервные копии шифруются. Ключи шифрования хранятся отдельно от данных.

14. Доступ к медицинским данным и операции их изменения записываются в защищённый журнал аудита.
