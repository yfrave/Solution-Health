# Стратегия горизонтального масштабирования

Для масштабирования выбраны две наиболее критичные системы:

* **Patient API / Mobile Backend** - принимает основную нагрузку от мобильного приложения;
* **Расписание** - отвечает за поиск слотов и создание записей, при этом в его базе уже возникают блокировки и дубли.

Нагрузка на 1С снижается с помощью сервиса полисов, кэша и очереди, описанных в Task 4.1. Саму 1С горизонтально 
масштабировать в рамках мобильного приложения нельзя.

| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Patient API / Mobile Backend** | Сервис не хранит сессии, файлы и состояние операций в памяти конкретного экземпляра. JWT проверяется на API Gateway. Состояние Saga и ключи идемпотентности хранятся в PostgreSQL, а кэш и счётчики ограничения запросов - в Redis. Запускается минимум 3 экземпляра сервиса в нескольких зонах отказа за балансировщиком. HPA автоматически изменяет их количество по CPU, RPS, времени ответа `p95` и размеру очередей | При увеличении числа экземпляров растёт количество соединений и запросов к PostgreSQL, Redis, 1С, LIS и платёжному шлюзу. Эти системы могут стать общими узкими местами                                | Для PostgreSQL используется пул соединений и реплики чтения. Redis запускается в кластере с репликацией. Нагрузка на внешние системы снижается с помощью кэша, очередей, тайм-аутов и автоматических выключателей. Общее количество соединений и повторных попыток ограничивается независимо от числа экземпляров Patient API                                                         |
| **Расписание**                   | Java-сервис запускается в нескольких экземплярах за балансировщиком и не хранит состояние локально. Поиск врачей и слотов выполняется через кэш и реплики PostgreSQL для чтения. Создание и изменение записи выполняются на основной базе. Все запросы создания принимают `Idempotency-Key`. При дальнейшем росте данные можно разделить по `cityId` или `clinicId`                                                      | Несколько пациентов могут одновременно попытаться занять один слот. Реплика чтения может отставать от основной базы, поэтому свободный в результатах поиска слот к моменту записи уже может быть занят | Перед созданием записи слот повторно проверяется в основной базе. Резервирование выполняется в короткой транзакции. Уникальное ограничение запрещает создать две активные записи на один слот. Для защиты от одновременного изменения используется поле `version` или блокировка `SELECT FOR UPDATE`. При достижении предела основной базы данные разделяются по городам или клиникам |

## Общие правила

* Экземпляры сервисов размещаются минимум в двух зонах отказа. Потеря одного экземпляра не должна останавливать работу приложения.
* Для Patient API запускается не менее трёх экземпляров. Количество экземпляров автоматически увеличивается при росте нагрузки.
* Масштабирование начинается до полной загрузки ресурсов. Основные показатели: `p99 < 1 с`, запас не менее 30% по CPU 
и отсутствие постоянного роста очередей.
* HPA имеет верхнее ограничение. Оно учитывает допустимое количество соединений к базе данных и пропускную способность зависимых систем.
* Бесконтрольное увеличение числа экземпляров запрещено, поскольку оно может перегрузить базу данных, 1С или платёжный шлюз.
* Нагрузочные тесты должны отдельно проверять поиск слотов, одновременную запись нескольких пациентов на один слот, 
остановку одного экземпляра и недоступность зависимых систем.
