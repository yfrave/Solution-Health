# Отказоустойчивость интеграций

## Параметры вызовов

В таблице указаны начальные настройки. После нагрузочного тестирования их нужно уточнить по времени ответа `p95/p99`, 
доле ошибок и общей длительности операции.

Повторные попытки выполняются только при технических ошибках: тайм-ауте, `429`, `502`, `503` и `504`. 
Бизнес-ошибки и остальные ответы `4xx` повторно не отправляются.

Адаптер 1С дополнительно ограничивает исходящий поток до **40 RPS**. Это значение ниже известного порога отказа в 50 RPS.

Одновременно разрешается не более **10 вызовов** к 1С. Для них используется отдельный пул соединений. Если 1С зависнет, 
она не займёт все ресурсы сервиса и не заблокирует другие интеграции.

Для платёжных операций `charge`, `status` и `refund` используются отдельные пулы соединений и отдельные автоматические 
выключатели. Сбой проверки состояния не должен блокировать возврат или создание нового платежа.

## Приоритет автоматического выключателя

В первую очередь автоматический выключатель (Circuit Breaker) нужен перед **1С**.

1С может зависать более чем на 30 секунд и перестаёт справляться с нагрузкой выше 50 RPS. Без автоматического 
выключателя медленные вызовы займут все соединения адаптера. Повторные попытки увеличат нагрузку, а сбой 1С 
распространится на запись и мобильное приложение.

Для платёжного шлюза автоматический выключатель тоже нужен. Но основная защита платежей - это `operationId`, 
идемпотентность и проверка состояния операции после тайм-аута. Сам автоматический выключатель не предотвращает двойное списание.

## Настройка автоматического выключателя для 1С

Используется скользящее окно из последних 20 вызовов. Для расчёта нужно получить не менее 10 вызовов.

Состояния автоматического выключателя:

* **Закрыт (`Closed`)** - запросы передаются в 1С. Если доля ошибок или ответов дольше 2 секунд достигает 50%, 
* автоматический выключатель открывается.
* **Открыт (`Open`)** - в течение 30 секунд запросы в 1С не отправляются. Сервис сразу использует кэш 
* или возвращает состояние `PENDING`.
* **Проверка восстановления (`Half-open`)** - после 30 секунд в 1С отправляются 3 пробных запроса. 
* Если все они успешны, обычная работа восстанавливается. При новой технической ошибке автоматический 
* выключатель снова открывается.

В систему наблюдения передаются:

* состояние автоматического выключателя;
* доля ошибок;
* доля медленных ответов;
* количество ответов из кэша;
* количество команд, ожидающих обработки.

Эти значения являются начальными и могут быть изменены после нагрузочного тестирования.

## Снижение нагрузки на 1С

Перед 1С добавляется **сервис полисов ДМС (DMS Policy Service)**. Он становится единственной системой, которая обращается к 1С.

Сервис выполняет следующие задачи:

* хранит данные полисов в Redis;
* возвращает недавно проверенные данные без обращения в 1С;
* объединяет одинаковые одновременные проверки одного пациента в один запрос;
* ограничивает исходящий поток до 40 RPS;
* помещает команды прикрепления полиса в очередь;
* повторяет неудачные команды по `operationId`;
* выполняет периодическую сверку данных с 1С.

Основной системой хранения полисов остаётся 1С. Кэш используется только для снижения нагрузки и ускорения ответа.

В ответе сервиса передаются поля `verifiedAt` и `dataFreshness`. Они показывают, когда данные последний раз проверялись 
и насколько они актуальны. Если данные устарели, сервис возвращает состояние `PENDING`, а не сообщает, 
что полис действителен или недействителен.

Периодическая контрольная сверка сравнивает данные кэша с 1С и исправляет пропущенные изменения.

## Использованные архитектурные стили

* **Синхронное взаимодействие** используется для чтения данных из кэша, когда приложению нужен быстрый ответ.
* **Асинхронное взаимодействие** используется для прикрепления полиса, фоновой проверки и обновления кэша. 
* Очередь позволяет обрабатывать запросы с той скоростью, которую выдерживает 1С.
* **Пакетная обработка** используется только для полной контрольной сверки по расписанию. 
* В обычный пользовательский сценарий она не входит.
